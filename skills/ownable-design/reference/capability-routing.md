# Capability routing

Load this when Ownable must choose tools for production, sourcing, media, or visual verification.

Ownable routes by **capability**, not vendor.

## 1. Inventory what exists

Relevant capabilities may include:

- code/file editing;
- browser/app rendering;
- screenshot/visual inspection;
- web/reference search;
- real-asset retrieval / connected libraries;
- image generation;
- image editing / masking / matting / background removal;
- vector/SVG/diagram creation;
- data visualization;
- motion/animation implementation;
- video generation/editing;
- 3D/spatial generation/rendering;
- audio generation/editing;
- external MCP/connector/plugin tools;
- safe local tools.

Do not assume the capability is unavailable because one familiar provider is absent.

## 2. Route the design need to the capability

Examples:

- transparent subject cutout → image editing/matting with alpha;
- authored watercolor memory → image generation;
- real hero photo with distracting background → image editing;
- facility/product/person proof → verified real-asset sourcing;
- exact process relationship → semantic diagram/vector/data construction;
- spatial object story → 3D/spatial capability when earned;
- continuity/state-change movement → motion implementation;
- “does this actually look right?” → render/screenshot/visual inspection.

Native tools, MCPs/connectors, local tools, or third-party services may fulfill the same role. Provider changes do not change the art-direction rule.

## 3. Pick tools by output requirements

When multiple tools can do the job, prefer the one that best satisfies:

1. truth/provenance;
2. required medium and controllability;
3. output quality;
4. alpha/file/format requirements;
5. consistency with existing assets;
6. iteration/inspection support;
7. known privacy, cost, or time constraints.

## 4. Source vs edit vs generate vs construct vs remove

- **source** when authenticity/proof is the reason the media matters;
- **edit** when the underlying real asset is right but presentation is weak;
- **generate** when synthetic/authored media is truthful for the role;
- **construct** when precision, responsiveness, semantics, or interaction matters;
- **remove** when media adds no value.

Do not regenerate reality because generation is easier.

## 5. Use available tools, not prompt-only advice

When a justified capability exists, perform the intervention rather than merely writing instructions for someone else.

If generation is justified, generate. If matting is needed and available, make the cutout. If rendering is available, inspect the render.

## 6. Fallback without lying

If the preferred capability is absent:

1. search the environment for an equivalent capability;
2. choose an alternate medium that preserves the concept when possible;
3. continue the rest of the work;
4. disclose the blocked part precisely.

Never pretend the intervention happened.

## 7. Portability

Ownable's reasoning is portable even when loading mechanisms differ.

- Agent Skills-compatible environments can install/load the skill directly.
- Project/system-instruction environments can include SKILL.md and needed references.
- Chat environments can attach the skill files as project context.
- MCPs/connectors/plugins/local tools can satisfy capabilities without changing Ownable's logic.

Core rules must not require any named provider.
